# macOS Storage Research

## Source

Apple - Free up storage space on MAC
https://support.apple.com/en-in/guide/mac-help/mchl3d437fbc/mac

## Findings

So, macOS's "System Data" is a broad category containing system and application related files that don't fit into the other storage categories.

Examples include:

- Logs
- Caches
- VM Files
- Temporary Files
- Runtime System Resources
- Application Support Files
- Fonts
- Other system-related resources

## Initial Observation

"System Data" doesn't appear to represent one specific directory which we can just simply delete.
So this project needs to identify which files and directories that can be safely managed rather than deleting the whole "System Data".

## Candidate Cleanup Categories

- Caches: I believe, we will have to investigate it when running the application and not just completely deleting all of it, as some caches are important. [INVESTIGATE]

- Logs: Similiar as cache, it will depend for each log files and we can't blindly delete all of it. [INVESTIGATE]

- Browser Cache/Service-Worker Data: Should be safe to touch it, as at worst it will log you out of some sites or reset offline app content. Although, it is not something preferred, overally it should be more safer than others. [INVESTIGATE]

- Temporary Files: Should be safe as they are temporary. [INVESTIGATE]

- Persistent Application Data: Should NOT be touched unless we are extremely carefull going through it. [DO NOT TOUCH]

- User Data: Same as persistent application data, it shouldn't be touched careless unless following some strict protocol. [DO NOT TOUCH]

## Initial Feature

The first version of this cleaner should ask for a directory then scan it and report and files/directories that match cleaning categories, including their sizes, BUT do not delete anything.

The main purpose is to understand what we are finding and determine what is safe to investigate and eventually delete, rather than outright deleting things from the get-go.

## Candidate Information

Information one reported candidate should contain:

- Path

- Size

- Category

- Safety Classification

- Reason - why the candidate received its safety classification

## Candidate Detection Rules

To go from raw file traversal to targeted candidate detection, the scanner evaluates items against rules based on name or extension.

All rules default to a safety classification of `investigate` to prevent accidental loss of user data or application state.

---

## 1. Caches

Generated or regenerated data that is commonly produced by runtimes or applications.

| Target Pattern | Match Strategy       | Category | Safety Classification | Reason                             |
| :------------- | :------------------- | :------- | :-------------------- | :--------------------------------- |
| `__pycache__`  | Directory exact name | `cache`  | `investigate`         | Python compiled bytecode directory |

Additional cache locations, such as application-specific cache directories, may be added later once their path context and safety can be established.

---

## 2. Logs

Diagnostic output files produced by applications, development tools, and system services.

| Target Pattern | Match Strategy | Category | Safety Classification | Reason                          |
| :------------- | :------------- | :------- | :-------------------- | :------------------------------ |
| `*.log`        | File extension | `log`    | `investigate`         | Application or runtime log file |

Specific system or application log directories may be supported later through scoped path rules rather than matching every directory named `Logs`.

---

## 3. Temporary Files

Short-lived files that may be created during application or system operations and can potentially be regenerated or discarded.

| Target Pattern | Match Strategy | Category    | Safety Classification | Reason                     |
| :------------- | :------------- | :---------- | :-------------------- | :------------------------- |
| `*.tmp`        | File extension | `temp_file` | `investigate`         | Temporary operational file |
| `*.temp`       | File extension | `temp_file` | `investigate`         | Temporary operational file |

Temporary directories such as `tmp` or `TemporaryItems` are not treated as candidates by name alone because the same directory names can represent legitimate application or project data.

---

## 4. System Metadata

Small files generated by macOS to store metadata about directories or their contents.

| Target Pattern | Match Strategy  | Category          | Safety Classification | Reason                            |
| :------------- | :-------------- | :---------------- | :-------------------- | :-------------------------------- |
| `.DS_Store`    | File exact name | `system_metadata` | `investigate`         | macOS Finder folder metadata file |

---

## Explicit Exclusions (Protected Boundaries)

The detection engine must explicitly treat these categories as out-of-bounds. They must never match a candidate rule.

* Persistent Application Data → DO NOT TOUCH

  *(e.g., SQLite databases, local state files, user preference `*.plist` files, and application support state stored outside explicitly recognized disposable locations)*

* User Data → DO NOT TOUCH

  *(e.g., Documents, Desktop, Downloads, media libraries, source code files, and personal files)*

Candidate detection identifies items that **may warrant investigation**. A match must never be treated as permission to delete the item.

The intended cleanup flow is:

SCAN → CLASSIFY → REPORT → USER APPROVAL → DELETE
